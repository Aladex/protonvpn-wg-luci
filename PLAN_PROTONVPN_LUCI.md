# protonvpn-wg-luci — план реализации

## Контекст

Третий представитель семейства после `nordvpn-luci` (v1.4.0, в проде) и
скелета `mullvad-wg-luci`. Цель — e2e-управление ProtonVPN с роутера: логин,
регистрация WireGuard-ключей, выбор серверов, ротация, watchdog, LuCI-страница.
Спека и результаты разведки — в `RECON.md` (читать первым). Скелет проекта
генерируется отдельно; этот план — про превращение скелета в рабочий продукт.

### Принятые решения
| Вопрос | Решение |
|--------|---------|
| Авторизация | **SRP-6a в браузере** (JS страницы LuCI, нативный BigInt), HTTP через rpcd/curl. Пароль не доходит до роутера. OAuth/device-code у Proton для третьих сторон нет. |
| Хранение пароля | **Не хранить.** На роутере только сессионные токены (0600) и приватный WG-ключ. |
| Истечение сессии | Не рвёт VPN (серт account-wide до 365д, ротация из кэша). Лестница уведомлений: тихий backoff → syslog+баннер «тоннель работает, войдите» → предупреждение при серте <30д → критично при истёкшем серте. |
| Отличать сбой сети от отказа auth | `expired` только на явный 401/invalid-refresh; транзиентные ошибки — в экспоненциальный backoff (переиспользуем паттерн watchdog). |
| Порядок работ | SRP **первым** — он проверяем офлайн на векторах и он же инструмент для съёма живых фикстур (без сессии `/vpn/logicals` отдаёт 401). |
| Секреты в разведке | Пароль Андрея **не попадает в транскрипт/файлы**: скрипт читает его из stdin или из временного файла, который удаляется в той же фазе. |
| Тесты SRP | `node` (v26 на дев-хосте) — компонентные тесты офлайн; финальная приёмка — живой 200 от `/auth` + верификация ServerProof. |
| Репозиторий и фид | **Отдельный репо** (`protonvpn-luci`) + своя пара ключей подписи + свой gh-pages фид. Независимые релизы, своя аудитория. |
| Secure Core / Tor | **Делаем и тестируем в v1** — аккаунт платный, живые серверы есть. |
| Порядок включения 2FA | **Сначала снимаем флоу БЕЗ 2FA** (фаза 2a) — изолируем корректность SRP. Потом Андрей включает TOTP, снимаем 2FA-ветку (фаза 2b). Не отлаживать SRP и 2FA одновременно. |
| **2FA** | **Включаем TOTP на аккаунте — рекомендуемая конфигурация.** Именно 2FA митигирует главный остаточный риск (SRP-JS отдаётся по HTTP: подменённый скрипт мог бы украсть пароль — но без TOTP пароль бесполезен). Фрикции нет: код спрашивается только при логине (≥30 дней), refresh идёт без 2FA. **Только TOTP** — FIDO2/WebAuthn через этот путь не работает; аккаунт с одним лишь аппаратным ключом наш логин сломает. В README: предупредить и напомнить про recovery-коды (протухшая сессия + потерянный TOTP-сид = с роутера не войти). |

### Что уже есть и НЕ требует изменений
- **`nordvpn-luci` как референс-архитектура**: два пакета, ucode-модули,
  procd-демон (30с тик), rpcd/ubus, LuCI JS view, подписанный opkg/apk-фид, CI.
- **Готовые к портированию модули** (концепции переносятся 1:1): `select.uc`
  (location sets), `rotate.uc` (handshake-verify + rollback + локи + persisted
  clock), `service.uc` (`should_refresh`/`should_rotate`/`next_rotation` +
  watchdog: `should_recover`/`watchdog_update`/`watchdog_result_update`),
  `routing.uc` (зоны/kill switch/IPv6-block/steering/MTU-рекомендация),
  `status.uc`, `apply.uc`.
- **Тест-харнесс**: `tests/run.sh` + `mocks/uci.uc` + `mocks/ubus.uc`
  (генерические, копируются как есть) + фикстурный подход
  (`fixtures/servers_sample.json`).
- **LuCI-виджеты**: Model B location-set (страна → чипы → города),
  load-aware server picker, ротация, инстансы, Advanced с watchdog-галкой.
- **CI**: сборка современного ucode из исходников для тестов, self-hosted NAS
  раннер для тегов, подпись и публикация фида на GitHub Pages.
- **Инфра-уроки**: `UCODE_EXTRA_L` пробрасывать дочерним процессам в тестах;
  `record()` мержит стейт под локом; аннотированные теги; никакой
  AI-атрибуции в артефактах; комментарии в коде только по-английски.

## Фаза 1: SRP-6a на JS (офлайн)

### Цель
Автономный JS-модуль, считающий Proton-SRP: из (`username`, `password`,
`salt`, `modulus`, `serverEphemeral`) → (`clientEphemeral`, `clientProof`) +
проверка `serverProof`.

### 1.1 RED: тесты
**Файл:** `luci-app-protonvpn/htdocs/luci-static/resources/view/protonvpn/srp.test.mjs`
(гоняется `node --test`; в опкг-пакет не попадает)
**Тесты:**
1. `modPow` на BigInt — известные малые значения + один 2048-битный кейс.
2. `bcrypt` — стандартные векторы (`$2y$`), включая Proton-вариант соли
   (base64-алфавит Proton, префикс версии).
3. Расширение хеша (expanded SHA-512) — против эталонных значений из
   опубликованной реализации Proton.
4. Полный SRP-раунд против **зафиксированного вектора**: подставляем известные
   `salt/modulus/serverEphemeral/password` и сверяем `clientProof`
   (вектор берём из go-реализации community-тула, проверяем перекрёстно).
5. Проверка `serverProof` — валидный проходит, изменённый отклоняется.
6. Отказ на вырожденных входах: `serverEphemeral % N == 0`, пустой modulus.

### 1.2 GREEN: реализация
**`srp.js`:**
- `modPow(base, exp, mod)` на BigInt (square-and-multiply).
- `bcryptHash(password, salt)` — завендорить компактную реализацию (лицензия
  совместима с MIT; версию/происхождение зафиксировать в шапке файла).
- `hashPassword(version, password, username, salt, modulus)`.
- `generateProofs(modulus, serverEphemeral, passwordHash)` → `{clientEphemeral,
  clientProof, expectedServerProof}`.
- Работа с base64 ↔ BigInt little-endian (у Proton именно LE — покрыть тестом).
- Никакой сети, никакого DOM — чистая функция, чтобы тестировалась в node и
  подключалась в LuCI как обычный ресурс.

### 1.3 REFACTOR
Вынести base64/LE-хелперы, если дублируются. Проверить, что файл проходит
`eslint` конфигом проекта.

### Отчёт фазы 1

**Статус: готово. 17/17 тестов проходят.**

**Главное достижение — кросс-проверка с эталоном.** Вместо самодельных векторов
сгенерировал их из **референсной реализации** `ProtonMail/go-srp` (MIT):
клонировал, добавил локальный `vector_test.go` с детерминированным CSPRNG
(`p[i] = (i+1) mod 256`, который `crypto/rand.Int` читает big-endian и который
воспроизводим в JS), прогнал и выгрузил значения в
`luci-app-protonvpn/tests/fixtures/srp_vectors.json`. Наш JS выдаёт
**побайтово те же** `clientEphemeral`, `clientProof` и `expectedServerProof` —
то есть порт согласован с клиентом Proton, а не просто «внутренне непротиворечив».

**Тесты (17):** `modPow` (малые + известные); LE↔BigInt round-trip и порядок
байт; `expandHash` для пустого входа, `"abc"` и длина 256; bcrypt против 3
protonовских `$2y$`-векторов; `hashPassword` v4 против эталона; отказ на
неподдерживаемой auth-версии; полный раунд пруфов против эталона; разные A при
двух вызовах без инъекции секрета; `verifyServerProof` (валидный / битый /
короткий); `checkParams` — неверная битность, не 3 mod 8, B вне границ,
валидный кейс, составной modulus (Lucas); отказ `generateProofs` на невалидном B.

**RED был продемонстрирован дважды.** Первый прогон дал ложный RED: `node --test`
с каталогом падал на разрешении пути, а не на отсутствии модуля. Переделал:
временно убрал `srp.js` → `Cannot find module .../srp.js`, `pass 0 / fail 1`;
вернул → `pass 17 / fail 0`. Тесты гоняются по файлу, не по каталогу.

**Реализация — `htdocs/luci-static/resources/view/protonvpn/srp.js`:**
UMD (работает и как CommonJS в node-тестах, и как обычный ресурс LuCI, где
кладётся в `window.ProtonSRP`). SHA-512 через WebCrypto (`crypto.subtle`), поэтому
API асинхронный. Экспортирует `expandHash`, `bcryptHash`, `bcryptBase64`,
`hashPassword`, `checkParams`, `generateProofs`, `verifyServerProof`, `modPow`,
LE-хелперы и `prepareLogin()` — одну функцию для логин-модалки, которая из
ответа `/auth/info` отдаёт готовые поля для `/auth`.

**Закрытые открытые вопросы:**
- **bcrypt (вопрос 3):** `bcryptjs@3.0.2` **точно воспроизводит** protonовские
  `$2y$`-векторы. Завендорен как `view/protonvpn/vendor/bcrypt.js` (UMD, 47 КБ,
  без модификаций) + `bcrypt.LICENSE`. Лицензия **BSD-3-Clause**, не MIT —
  совместима с распространением, но требует сохранения копирайта (сделано); это
  стоит упомянуть в README проекта.
- **PGP-подпись Modulus (вопрос 2):** можно **не тащить openpgp.js в v1**.
  Референс проверяет подпись *в дополнение* к математической валидации, а
  именно валидация и защищает от подсунутой слабой группы: 2048 бит, `N ≡ 3 mod 8`,
  `1 < B < N-1` и **Lucas-тест** (`2^((N-1)/2) ≡ -1 mod N`) — один modexp,
  реализован и покрыт тестом на составном модуле. Плюс сам ответ приходит на
  роутер по HTTPS. PGP-верификацию оставляем как усиление на будущее.

**Отклонения от плана:**
1. Тесты лежат в `luci-app-protonvpn/tests/`, а не рядом с `srp.js` в `htdocs/`
   — иначе тест-файл попал бы в устанавливаемый пакет.
2. `eslint.config.mjs` дополнен: `vendor/**` исключён из линта (чужой код),
   для `srp.js` добавлены node/commonjs-глобалы (он двусредный).

**Регрессия:** `npx eslint luci-app-protonvpn` — чисто (0 ошибок, 0
предупреждений). Скелетный ucode-сьют (`protonvpn-wireguard/tests/run.sh` на
свежесобранном ucode) — **ALL TESTS PASSED**. Node-сьют — 17/17.

**Осталось для фазы 9 (не блокер):** тонкая LuCI-обёртка, которая подключит
`vendor/bcrypt.js` и `srp.js` как ресурсы страницы и вызовет `prepareLogin()`;
плюс убедиться, что оба файла попадают в пакет (`Makefile` устанавливает
`htdocs` целиком — проверить, что `vendor/` не отфильтрован).

## Фаза 2: Живой прогон и фикстуры

### Цель
Доказать, что SRP из фазы 1 работает против настоящего API, и снять реальные
формы ответов в фикстуры для всех последующих фаз.

### 2.1 RED: тесты
Приёмка живая, не юнит: скрипт-харнесс `tools/recon-login.mjs` (в пакет не
входит) должен получить **HTTP 200** от `/auth` и успешно проверить
`ServerProof`. До фазы 1 он не может этого сделать — это и есть RED.

### 2.2 GREEN: реализация
- `tools/recon-login.mjs` — node-скрипт: читает логин из аргумента, **пароль из
  stdin** (или из файла, удаляемого сразу после), делает `/auth/info` → SRP
  (модуль фазы 1) → `/auth` → при необходимости TOTP → `/auth/refresh` →
  `GET /vpn/logicals` → `POST /vpn/v1/certificate` (session-only, 7д, чтобы не
  мусорить в дашборде) → `DELETE`.
- Сохранить **санитизированные** ответы в
  `protonvpn-wireguard/tests/fixtures/`: `logicals_sample.json` (урезать до
  ~10 логикалов, но сохранить все варианты Features/Tier/SecureCore/Tor),
  `certificate_sample.json`, `auth_info_sample.json`, `auth_sample.json`.
  Из фикстур вычистить токены/UID/ключи, заменить на явные плейсхолдеры.
- Зафиксировать в `RECON.md`: точные значения Features-битмаски, лимит
  сертификатов, рабочее значение `x-pm-appversion`, поведение при captcha.
- **Проверить скоуп сессионного токена (важно для security-раздела README):**
  даёт ли VPN-логин полноценный account-токен (тогда украденный с роутера
  токен = доступ к почте) или ограниченный VPN-скоуп. Проверять чтением
  безобидного не-VPN эндпоинта тем же токеном; результат определяет, насколько
  строго формулировать риски в README.
### Разбиение фазы 2 по 2FA

- **2a (сейчас, 2FA выключена):** чистый SRP-раунд без лишних переменных —
  `/auth/info` → `/auth` (ждём 200 + валидный ServerProof) → `/vpn/logicals`
  → certificate create/delete. Это приёмка фазы 1.
- **2b (после 2a, Андрей включает TOTP):** `/auth` возвращает скоуп «нужен
  2FA» → `POST /auth/2fa`; зафиксировать форму ответа и поведение при неверном
  коде (нужна возможность переввести код **без** повтора SRP).

### Гигиена секретов в фазе 2

Скрипт **печатает только структуру** (счётчики, имена полей, коды ответов) —
никогда токены/пароль/приватные ключи. Полные ответы пишет в файлы, которые
санитизируются в фикстуры и затем удаляются. Пароль подаётся **через stdin
скрытым вводом**, запускает скрипт сам Андрей (`! node tools/recon-login.mjs
<login>`), чтобы пароль не попал ни в транскрипт, ни в историю команд.
- Удалить временные файлы с паролем/токенами; убедиться, что в репо не попало
  ничего секретного.

Нет.

### Отчёт фазы 2

**Статус: 2a выполнена (2026-07-30). Пароль в транскрипт не попал.**

Пошли не node-скриптом, а через **спайк на роутере** (Андрей был на remote):
задеплоили `api.uc` (реальные `auth_info`/`auth_finish`/`totp`/`refresh`/`logout`
+ `api_call` с секретами через анонимный пайп, не через argv), rpcd-методы,
`session_state` и одноразовую страницу `login-spike.js`. Пароль вводился в LuCI
(у Андрея по **HTTPS**), SRP считался в браузере.

**Результат логина — с первого раза:** `/auth/info` OK (version=4, modulus
clear-signed) → proof в браузере → `/auth` OK → **`server proof VERIFIED`** →
сессия на роутере (файл `0600`). Это приёмка фазы 1 на живом API.

**Снято по живой сессии (детали в RECON.md, раздел «Живая разведка»):**
- **Сертификат требует PEM Ed25519**, не сырой WG-ключ (400/Code 2001). Их
  генератор ключей отдаёт приватник клиенту — не используем. Локальная
  генерация через `openssl genpkey -algorithm ED25519` **принята (HTTP 200)**;
  WG-приватник = 32-байтный ed25519 seed. → зависимость **`openssl-util`**.
- Ответ сертификата содержит **`RefreshTime`** — используем его вместо нашего
  порога «<30 дней». `Mode` по умолчанию `"session"`, `Duration` = `"1 day"`.
  DELETE session-сертификата запрещён скоупом (403/9100) — только истечение.
- **Скоуп токена не даёт почту** (403/9100 на mail-эндпоинтах) — security-раздел
  README формулировать точно.
- **`/vpn/logicals` = 13.4 МБ / 18123 логикала**, ucode парсит 2.4 с на 1 ГБ
  RAM. Проектное ограничение для `cache.uc`.
- **Features-битмаска расшифрована**: 1=SecureCore, 2=Tor, 4=P2P, 8=Streaming,
  16=IPv6. `Tier` 2=платный, 0=free.
- Фикстура `logicals_sample.json` пересобрана из живого ответа (10 логикалов,
  все варианты Features + оба Tier).

**2b выполнена (тот же день).** Андрей включил TOTP; логин прошёл:
`server proof VERIFIED` → `2FA required` → **`TOTP accepted — session upgraded`**.
Найденное:
- Настоящий путь — **`POST /auth/2fa`** (`/auth/v4/2fa` — алиас). Изначальная
  догадка `/auth/v4/2fa/totp` давала 404; признак верного пути — 422 `Code 8002`
  на неверном коде. Неверный код **не** рушит сессию: код можно переввести без
  повтора SRP (как и задумано).
- **Включение 2FA не инвалидирует уже выданную сессию.**
- **CAPTCHA (`Code 9001`) реальна**, но транзиентна: сработала после нескольких
  логинов подряд, через несколько минут отпустила. Живая сессия при этом
  работала. В `api_error()` — внятное сообщение (подождать, не долбить, fallback).
- **Исправлен баг модели сроков:** `ExpiresIn` = TTL access-токена (1800 с при
  логине, 2592000 с после refresh), а не срок сессии. Теперь в стейте две
  шкалы — `access_expires_at` / `session_expires_at`; `/auth/refresh` проверен
  живьём (`ok: true`, токены ротированы, `RefreshCounter` растёт).

Итого фаза 2 закрыта целиком: весь auth-контур (SRP + 2FA + refresh +
certificate) подтверждён на живом аккаунте.

## Фаза 3: Фундамент бэкенда — `common.uc` + хранение сессии

### Цель
Настройки, валидаторы, константы и безопасное хранение сессионных токенов.

### 3.1 RED: тесты

**Тесты:**
