# ProtonVPN e2e для OpenWrt/LuCI — разведка

_Разведка от 2026-07-30. **Обновлено после живого прогона на платном аккаунте**
через LuCI-спайк на роутере: авторизованные эндпоинты проверены по-настоящему —
см. раздел «Живая разведка (фаза 2a)». План реализации — `PLAN_PROTONVPN_LUCI.md`._

## Цель

Третий представитель семейства (после nordvpn-luci и mullvad-wg-luci):
управлять ProtonVPN с роутера — логин, регистрация WireGuard-ключей, выбор
серверов, ротация, watchdog, LuCI-страница. Архитектура клонируется с
nordvpn-luci (backend `protonvpn-wireguard` + фронтенд `luci-app-protonvpn`).

## Главный вывод разведки

**ProtonVPN — самый сложный из трёх по авторизации, но самый богатый по
данным серверов.** Два факта определяют всю архитектуру:

1. **Авторизация — SRP-6a** (Secure Remote Password, с PGP-подписанным
   модулем), не токен (Nord) и не номер аккаунта (Mullvad). SRP требует
   bignum-арифметики (2048-бит modexp), которой в ucode нет и не будет.
2. **Список серверов — ТОЛЬКО за авторизацией.** Проверено живьём:
   `GET /vpn/logicals` без сессии → **401** (с валидным `x-pm-appversion`
   вида `linux-vpn@4.9.0`) или **422/Code 5003** «app version outdated»
   (с невалидным). Публичного relay-list, как у Mullvad, нет. Значит без
   решения auth-проблемы нет даже ротации по вставленному ключу.

## Решение auth-проблемы (ключевая дизайн-идея)

**SRP считать в браузере, HTTP гонять через роутер:**

- LuCI-страница исполняется в браузере пользователя, где есть нативный
  `BigInt` — SRP-6a реализуем на чистом JS без зависимостей.
- CORS не мешает: браузер НЕ ходит на api.protonvpn.ch напрямую. Флоу:
  rpcd (curl) делает `POST /auth/info` → получает salt/modulus/serverEphemeral
  → отдаёт браузеру → JS считает clientEphemeral+clientProof (BigInt) →
  rpcd отправляет `POST /auth` → получает сессию (UID, AccessToken,
  RefreshToken). TOTP 2FA — дополнительным шагом после auth.
- **SRP нужен только при первичном логине.** Дальше роутер сам держит
  сессию: `/auth/refresh` по RefreshToken (ротируется), сессия живёт 30
  дней и автопродлевается демоном. Re-login (SRP, руками) — только если
  refresh протух (роутер лежал >30 дней).
- Секрет-гигиена: пароль Proton существует ТОЛЬКО в браузере на время SRP
  (в этом весь смысл SRP — пароль не передаётся); на роутере хранятся
  сессионные токены + приватный WG-ключ.

Альтернативы отброшены: Go/Rust-хелпер на роутере — против философии
(pure ucode + curl) и ломает all-arch пакеты; python3 — ~5+ MB зависимостей;
openssl CLI не умеет произвольный modexp. OAuth/device-code («роутер показывает
ссылку, юзер авторизуется на сайте провайдера») **недоступен** — публичного
OAuth для третьих сторон у Proton нет.

### UX логина (важно: без редиректов)

LuCI-страница сама исполняется в браузере, поэтому «браузерная часть» — это JS
той же страницы, а не отдельная вкладка на proton.me. Флоу: **Log in** →
модалка (логин / пароль / TOTP) → страница показывает «Session active, expires
…» и подтягивает список серверов. Никуда не переходим, ничего не копируем.
Модалка нужна повторно не чаще раза в 30 дней (и только если refresh протух).

### Оговорка: HTTP vs HTTPS

Пароль вводится в страницу, отданную роутером по HTTP (если не настроен
`luci-ssl`). SRP не передаёт пароль, но JS, который считает доказательство,
приходит по незащищённому каналу — MITM в LAN может подменить скрипт и утащить
пароль. Документировать в README прямым текстом и рекомендовать LuCI по HTTPS.

## API (проверено живьём, если не указано иное)

База: `https://api.protonvpn.ch` (заголовок `x-pm-appversion` обязателен,
устаревшая версия → Code 5003; community-тулзы штампуют версию текущего
Linux-клиента).

| Эндпоинт | Auth | Что | Статус |
|---|---|---|---|
| `POST /auth/info` | — | SRP-параметры: `Modulus` (PGP clear-signed), `ServerEphemeral`, `Salt`, `SRPSession`, `Version`(=4) | ✅ 200 |
| `POST /auth` | SRP proof | → сессия: `UID`, `AccessToken`, `RefreshToken`, `ExpiresIn`, `Scope`, `ServerProof` | ✅ 200 (+ 422/9001 captcha) |
| `POST /auth/2fa` | сессия | `{TwoFactorCode}`; 8002 = неверный/использованный код. Алиас `/auth/v4/2fa`. FIDO2 не поддерживается | ✅ путь подтверждён |
| `POST /auth/refresh` | RefreshToken | продление сессии (токен ротируется, single-use) | реализовано, живьём не гоняли |
| `GET /vpn/logicals` | **сессия** | LogicalServers: Name, Load, **Score**, Tier, Features, Servers[] (EntryIP/ExitIP, Domain, X25519PublicKey) | ✅ 401 без auth (живьём) |
| `POST /vpn/v1/certificate` | сессия | `{ClientPublicKey (PEM Ed25519!), Duration:"1 day", Mode?}` → `SerialNumber`, `Certificate`, `ExpirationTime`, **`RefreshTime`**, `ServerPublicKey` | ✅ 200 (400/2001 на сырой WG-ключ) |
| `GET /vpn/v1/certificate/key/EC` | сессия | генерирует пару и отдаёт приватник — **НЕ использовать** | ✅ 200 |
| `DELETE /vpn/v1/certificate` | сессия | отзыв: для session-режима **запрещён скоупом** (403/9100) | ✅ 403 |

## Хранение пароля и истечение сессии (принятое решение)

**Пароль Proton НЕ хранится на роутере — ни в UCI, ни в файле.** Обоснование:
это пароль ко всему Proton Account (почта/Drive/Calendar), а не к одной
VPN-подписке; OpenWrt не умеет шифровать хранилище, любой root-процесс читает
`/etc`, и такой файл попадает в `sysupgrade`-бэкап, который люди складывают в
облака. При browser-SRP пароль вообще не доходит до роутера (в этом смысл SRP),
так что «не хранить» здесь дешевле обычного. На роутере живут только сессионные
токены (UID/Access/Refresh, файл 0600) и приватный WG-ключ.

Цена решения — раз в ≥30 дней (если refresh протух) нужен ручной ре-логин.
Поэтому обязателен явный, но не паникующий флоу уведомления.

### Ключевой факт: смерть сессии ≠ обрыв VPN

Сертификат **account-wide** и живёт до 365 дней, а ротация выбирает из
**кэша** — значит без живой сессии продолжают работать: тоннель, плановая
ротация, watchdog-восстановление. Ломается только то, что требует API:
обновление списка серверов (кэш стареет), новые действия и — главное —
**renew сертификата**. Настоящий дедлайн, о котором нужно предупреждать, это
`certificate.expires_at`, а не `session.expires_at`.

### Машина состояний сессии

`no_session` (не логинились) → `active` → `refreshing_failed` (транзиентно)
→ `expired` (нужен SRP-ре-логин) ; плюс `needs_2fa` и `blocked`
(captcha/human verification — из LuCI не решается, нужен fallback).

**Отличать сетевой сбой от отказа авторизации.** Лежащий WAN или DNS не должен
объявлять сессию мёртвой: `expired` ставится только на явный
authentication-отказ API (401/invalid refresh token), а транзиентные ошибки
уходят в тот же экспоненциальный backoff, что и watchdog (переиспользовать
паттерн `should_recover`, не долбить `/auth/refresh` каждые 30с).

### Лестница уведомлений (по нарастанию)

1. **Транзиентный сбой refresh** — тихо, backoff, без беспокойства юзера.
2. **`expired`** — `log()` в syslog (`logread -e protonvpn`), флаги в ubus
   `status`, спокойный баннер в LuCI: «сессия истекла, тоннель работает;
   войдите, чтобы обновлять список серверов и продлить сертификат» + кнопка
   **Re-login**, открывающая SRP-модалку.
3. **Серт истекает < 30 дней при мёртвой сессии** — баннер становится
   предупреждающим (называть дату), syslog-warning; это последнее окно, когда
   ре-логин ещё спасает без разрыва.
4. **Серт истёк** — тоннель реально не поднимется: критический баннер,
   `status.state` отражает причину (не просто «disconnected»).

### Что отдаёт ubus `status` (для LuCI и внешнего мониторинга)

`session: { state, expires_at }`, `certificate: { expires_at, mode }`,
`action_required: null | 're_login' | 'totp' | 'captcha'`. LuCI-баннер строится
только на этих полях. Баннер виден лишь тому, кто открыл LuCI, поэтому syslog
обязателен — его люди мониторят (и он ловится нашим VictoriaLogs).

### Fallback для `blocked`/captcha

Документировать в README путь «залогиниться десктопным
инструментом/официальным клиентом и вставить токены сессии в роутер руками» —
некрасиво, но снимает тупик, когда Proton требует human verification.

## Модель WireGuard-подключения

- Клиентский keypair генерится **локально** (`wg genkey`, как у Mullvad),
  наружу уходит pubkey через certificate-регистрацию.
- Сертификат **account-wide**: один ключ ходит на ЛЮБОЙ сервер — меняется
  только peer pubkey (`X25519PublicKey` конкретного сервера) + endpoint.
  Идеально для ротации.
- Адрес клиента фиксированный для всех: `10.2.0.2/32` (+ IPv6
  `2a07:b944::2:2/128`) — как у Nord (10.5.0.2), не как у Mullvad.
- DNS in-tunnel: `10.2.0.1` (IPv6 `2a07:b944::2:1`).
- Порт: стандартный 51820 UDP.
- **Срок сертификата — до 365 дней** → демону нужен renew-флоу (по живой
  сессии, без SRP; продлевать заранее, как cache-refresh).

## Отличия от Nord/Mullvad (сводно)

| | NordVPN | Mullvad | ProtonVPN |
|---|---|---|---|
| Credential | токен → API отдаёт ключ | 16-значный номер | **логин+пароль через SRP** (+TOTP) |
| Живучесть credential | токен бессрочный | номер вечный | сессия 30d (авторефреш), серт ≤365d (renew) |
| Ключ | серверный | локальный | локальный |
| Список серверов | публичный | публичный | **только за auth** |
| Load на серверах | есть (%) | нет (weight) | **есть: Load + Score** (Quick Connect = min Score) |
| Tunnel address | 10.5.0.2/32 у всех | per-device | 10.2.0.2/32 у всех |
| Multihop-аналог | Double VPN | порт-схема | **Secure Core** (Features bitmask) |
| Tor-аналог | Onion over VPN | нет | **Tor-серверы** (Features bitmask) |
| Бесплатный тариф | нет | нет | **есть (Tier 0)** — приложение заработает и на free |
| Слоты/лимиты | один ключ | 5 devices | сертификаты (лимит уточнить; persistent видны в дашборде) |

## Живая разведка (фаза 2a, выполнена 2026-07-30)

Проверено на платном аккаунте через LuCI-спайк на роутере: SRP-логин прошёл
**с первого раза**, `ServerProof` **верифицирован**, математическая валидация
группы (2048 бит, 3 mod 8, Lucas) отработала. `PM_APPVERSION = linux-vpn@4.9.0`
принимается. Дальше — снято по живой сессии (пароль при этом не требовался).

### ⚠️ Ключевое: сертификат требует Ed25519, а не сырой WG-ключ

`POST /vpn/v1/certificate` с base64 от `wg genkey` → **400, Code 2001**
(«не удаётся прочитать ключ»). `ClientPublicKey` должен быть **PEM
Ed25519** (SPKI OID `1.3.101.112`, префикс base64 `MCowBQYDK2VwAyEA`).

У Proton есть `GET /vpn/v1/certificate/key/EC`, который генерирует пару и
отдаёт **приватный ключ клиенту** — им пользоваться **нельзя**, это ломает
свойство «ключ не покидает роутер».

**Решение (проверено, HTTP 200):** генерировать локально —
`openssl genpkey -algorithm ED25519` (на роутере **OpenSSL 3.0.17**, Ed25519
поддержан; его публичный PEM байт-в-байт того же формата, что у Proton).
Seed (32 байта) = хвост 48-байтного PKCS#8 DER
(`openssl pkey -outform DER | tail -c 32`).

**WG-приватник = `SHA-512(seed)[0:32]`, а НЕ сам seed.** Первая догадка была
«seed и есть WG-ключ» — она стоила полдня. Proton хранит наш Ed25519-паблик и
выводит ожидаемый X25519 бирациональным отображением Эдвардса→Монтгомери, а
оно соответствует *расширенному скаляру* Ed25519, то есть `SHA-512(seed)[0:32]`
(это же делает libsodium `crypto_sign_ed25519_sk_to_curve25519`). Клампить
самим не надо: и `wg pubkey`, и ядро клампят приватник при использовании.

**Как выглядит ошибка (важно — она НЕ похожа на ошибку ключа):** handshake
проходит, `10.2.0.1` отвечает на ping за нормальные 25–30 мс, счётчики wg
шевелятся — но наружу не уходит ничего, DNS Proton молчит, а
`GET /vpn/v1/sessions` показывает ноль сессий. Сервер Proton принимает
инициацию от незнакомого ключа и лишь потом сверяется с базой авторизации.
Проверено живьём 2026-07-30: замена ключа на правильную деривацию сразу дала
трафик и выход через хорватский IP.

Порядок: `printf %s "$seed_b64" | openssl enc -base64 -d -A |
openssl dgst -sha512 -binary | head -c 32 | openssl enc -base64 -A`.

→ **Зависимость пакета: `openssl-util`.** И: в busybox **нет `base64`**,
использовать `openssl enc -base64 -A`. **`xxd` в busybox тоже нет** —
байты PKCS#8-префикса печатать восьмеричными escape'ами через `printf`.

### Ответ сертификата (формы полей)

`SerialNumber`, `ClientKeyFingerprint`, `ClientKey` (наш PEM), `Certificate`
(PEM), `ExpirationTime`, **`RefreshTime`** (сервер сам говорит, когда
перевыпускать — использовать его вместо нашего порога «<30 дней»),
`Mode` (без явного `Mode` → `"session"`), `Features`, `ServerPublicKeyMode: "EC"`,
`ServerPublicKey`. `Duration` принимается строкой вида `"1 day"`.
**Сертификаты не отзываются вообще.** `DELETE /vpn/v1/certificate` → 403
`Code 9100` («токен доступа не имеет доступа») и для session-, и для
**persistent**-сертификатов; ни тело, ни query-параметр не помогают, путь с
сегментом даёт 404. Отзывать умеет только полная веб-сессия на
account.protonvpn.com. Практическое следствие: **удалённый инстанс оставляет
свой сертификат занимать слот до самого истечения** — при `CERT_MAX_DAYS`
это год. Проверено живьём: после двух тестовых инстансов на аккаунте висело
четыре сертификата при одном живом тоннеле.

### 2FA: путь `/auth/2fa` (не тот, что был в догадке)

Проверено пробой на сессии: `POST /auth/2fa` → 422 `Code 8002` «неверные
учётные данные» (путь **существует**, код просто фейковый), `/auth/v4/2fa` —
рабочий алиас, `/core/v4/auth/2fa` тоже отвечает. Неверный путь даёт **404**,
чем изначальная догадка `/auth/v4/2fa/totp` и оказалась. Body: `{"TwoFactorCode": "..."}`.

**Включение 2FA НЕ инвалидирует уже выданную сессию** — проверено: сессия,
полученная до включения TOTP, осталась `active`, токен продолжал работать
(`/vpn/logicals` → 200). Значит TOTP спрашивается только при новом логине.

### ⚠️ CAPTCHA (Code 9001) — риск подтверждён на практике

После нескольких логинов подряд с одного IP `/auth` вернул **422, Code 9001**:
«For security reasons, please complete CAPTCHA… try updating your app or contact
us». Из LuCI капчу решить нельзя. Наблюдения:

- Триггерится **частотой попыток**, а не самим нашим клиентом (первый логин
  прошёл идеально).
- **Живая сессия при этом продолжает работать** — капча блокирует только
  получение новой. То есть это не «сервис лёг», а «нельзя перелогиниться сейчас».
- Повторные попытки делают хуже. В `api_error()` добавлено внятное сообщение:
  подождать, не долбить, при отсутствии сессии — войти официальным клиентом и
  импортировать сессию.
- Гипотеза на будущее (не проверяли, чтобы не долбить API): официальные клиенты
  посылают полноценный `User-Agent`, а мы — нет; возможно, это влияет на порог
  срабатывания. Проверить в спокойный момент, добавив реалистичный UA.

Вывод для продукта: **обязателен документированный fallback** и мягкая
обработка 9001 в UI. Первичная настройка — самый уязвимый момент; после неё
роутер живёт на refresh-токене месяцами и логин больше не нужен.

### Два разных срока: access-токен 30 минут, сессия 30 дней

**Важно, я это сначала перепутал.** `ExpiresIn` из `/auth` — TTL **access-токена**,
а не сессии. Измерено живьём: при логине `ExpiresIn = 1800` (30 минут).
Трактовка его как «срок сессии» приводила бы к «сессия истекла, войдите заново»
каждые полчаса — ровно то, чего мы избегаем.

Проверено `/auth/refresh` (HTTP 200, поля: `AccessToken`, `ExpiresIn`,
`TokenType: Bearer`, `Scope`/`Scopes`, `Uid`/`UID`, `RefreshToken`, `LocalID`,
**`RefreshCounter`**): после refresh `ExpiresIn = 2592000` (**30 дней**). То есть
короткие 30 минут выдаются только при первичном логине, а обновлённый токен
живёт долго. Refresh-токен ротируется и **одноразовый** — сохранять новую пару
обязательно, иначе следующий refresh провалится навсегда.

Поэтому в состоянии сессии **две шкалы**:
`access_expires_at` (когда демону молча звать refresh, порог 300 с) и
`session_expires_at` (~30 дней; только его истечение требует ре-логина).
Истечение access-токена **никогда** не показывается пользователю как «войдите».
`RefreshCounter` можно использовать в диагностике.

### Мульти-инстанс: лимит — 11 ОДНОВРЕМЕННЫХ подключений, сертификаты бесплатны

`GET /vpn` (и `/vpn/v2`) на платном аккаунте отдаёт:
`PlanTitle: "VPN Plus"`, `MaxTier: 2`, **`MaxConnect: 11`**, `Groups: ["vpn-paid"]`,
плюс `NetShield: { Malware, AdsAndTrackers, AdultContent }`.

**`MaxConnect` считает активные сессии, а не зарегистрированные ключи.**
Доказательство: `GET /vpn/v1/sessions` → `{"Sessions": []}` при том, что на
аккаунте уже зарегистрировано несколько наших сертификатов. То есть
зарегистрированный, но не подключённый сертификат слот **не занимает**.

Следствия для дизайна:
- Схема «инстанс = свой интерфейс + свой keypair + свой сертификат» (как
  реализовано) **бесплатна** в терминах лимита; платим только за реально
  поднятые тоннели. Роутер с 2–4 инстансами оставляет 7–9 слотов на телефон
  и ноутбук.
- Делить один ключ между инстансами **не нужно** и рискованно: один и тот же
  ключ, одновременно подключённый к двум серверам, — неопределённое поведение
  на стороне Proton. Изоляция per-instance безопаснее и ничего не стоит.
- `GET /vpn/v1/certificate` → 405 `Allow: DELETE, POST`, но список всё же
  есть: **`GET /vpn/v1/certificate/all?Mode=persistent&Limit=50`** с
  постраничным `BeginID`. Свой `certificate.json` всё равно нужен (в нём
  лежит seed), но сирот теперь можно и найти, и почистить.
- **`GET /vpn/v1/sessions` для WireGuard бесполезен**: он считает легаси
  OpenVPN/IKEv2-сессии и возвращает пустой массив при живом тоннеле,
  качающем мегабайты (проверено). Карточка аккаунта, построенная на нём,
  показывала «0 из 11» при двух поднятых тоннелях. Считать надо
  **зарегистрированные сертификаты** через
  `GET /vpn/v1/certificate/all?Mode=persistent&Limit=50` (постранично по
  `BeginID`) — это и есть занятые слоты устройств для WireGuard.

Осторожно: `/vpn` также возвращает `Name` и `Password` — это **легаси-креды
OpenVPN/IKEv2**. Для WireGuard они не нужны; логировать и показывать их нельзя.

Задел на будущее: `NetShield` (блокировка рекламы/малвари) — у Proton это
DNS-механика. `certificate_create` шлёт `Features` объектом
(`NetShieldLevel: 0, RandomNAT: true, PortForwarding: false, SplitTCP: true`)
и `ClientPublicKeyMode: "EC"`, как это делают клиенты Proton; если `Features`
опустить, ответ приходит с бесполезным `Features: []`. `RandomNAT` —
инвертированный флаг: `true` означает «без Moderate NAT», `SplitTCP` — это
VPN Accelerator. На маршрутизацию трафика ни одно из полей не влияет
(проверено): их отсутствие было ложным следом при разборе тишины в тоннеле.

### Скоуп токена — лучше, чем опасались

`scope = "self parent user loggedin vpn verified settings"`. Пробы почтовых
эндпоинтов (`mail.proton.me/api/mail/v4/messages`,
`api.protonmail.ch/mail/v4/conversations`) → **403, Code 9100** «токен доступа
не имеет доступа». Значит украденный с роутера токен даёт VPN и настройки
аккаунта, но **не почту/Drive**. В README формулировать именно так (не
запугивать, но и `user`/`settings` в скоупе не замалчивать).

### `/vpn/logicals`: 13.4 МБ — это проектное ограничение

Авторизованный ответ: **13 463 012 байт, 18 123 логикала** (публичный
неавторизованный отдавал ~158 КБ / 563 — то есть на платном аккаунте виден
весь парк). Все 18 123 имеют `X25519PublicKey`. 148 стран, 193 города.
`ucode` на этом роутере распарсил за **2.4 с** (1 ГБ RAM) — работает, но на
роутере со 128 МБ это риск. Кэш обязан быть компактным нормализованным, а
парсинг — редким (раз в N часов), не на каждый запрос UI.

## Что переиспользуется из nordvpn-luci

- Вся архитектура: 2 пакета, ucode-модули, procd-демон (30с тик), rpcd/ubus,
  LuCI JS view, подписанный opkg/apk-фид, CI на NAS.
- `cache.uc` — logicals → внутренний формат стран/городов/relays (у Proton
  есть City в логикалах; нормализация прямая).
- `select.uc` — **location sets** как есть.
- `rotate.uc` — handshake-verify + rollback + локи: как есть.
- `service.uc` + **watchdog** (1.4.0): как есть; плюс два новых периодических
  джоба того же паттерна: session-refresh и certificate-renew.
- `routing.uc`, `status.uc`: как есть.
- LuCI: Model B локейшн-виджет, **load-aware server picker переносится
  напрямую** (Load есть; сортировка по Score = родной Quick Connect),
  hop-mode-переключатель превращается в Standard / Secure Core / Tor.

## Что пишется заново

- `api.uc`: SRP-релейный флоу (info → браузер → auth), refresh, certificate
  CRUD; хранение сессии (UID/Access/Refresh) в защищённом сторадже.
- **SRP-JS в LuCI** (BigInt): единственный по-настоящему новый и рискованный
  компонент. Референсы: go-код `hatemosphere/protonvpn-wg-confgen`
  (internal/auth), официальные Proton-клиенты (open source).
- Верификация PGP-подписи modulus (опционально; можно зашить known modulus).
- UI: логин-модалка (логин/пароль/TOTP), статус сессии и срока сертификата,
  renew-кнопки.

## Открытые вопросы

- **PGP-подпись Modulus**: честная верификация (тащить openpgp.js в LuCI) или
  пиннинг известных модулей по хешу — не решено.
- **bcrypt для SRP**: Proton прогоняет пароль через bcrypt (auth version 4);
  в браузере нативного нет → вендорить чистый JS-bcrypt (~10–20 КБ) в
  luci-app. Вторая криптозависимость после BigInt-модекспа.
- **Нужен Proton-аккаунт для второй фазы разведки** — живьём прогнать
  /auth/info → /auth → /vpn/logicals → /vpn/v1/certificate (хватит даже
  free). Без этого точные поля запросов/ответов — по чужому коду.
- Точные значения `x-pm-appversion`, принимаемые API (community штампует
  версию актуального Linux-клиента; протухшие режутся 5003) — риск
  периодического обновления константы.
- Лимит на количество активных сертификатов.
- Features-bitmask значения (SecureCore/Tor/P2P/…) — снять с живого ответа.
- Secure Core в v1 или отложить (как multihop у Mullvad).
- Свободна ли ниша: luci-app-protonvpn в OpenWrt-фидах отсутствует (как и
  для Nord/Mullvad было).
